# Commit

변경사항을 분석해 컨벤션에 맞게 커밋한다. 사용자 승인을 따로 받지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석

먼저 저장소 상태를 확인한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고
```

- git 저장소가 아니면 커밋하지 말고, `git init`이 필요한지 사용자에게 묻는다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 끝낸다.
- 새 파일(untracked)은 `git diff`에 나오지 않으므로 `git status`로 확인하고 내용을 읽는다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, `dist` 같은 빌드 산출물은 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

변경 파일을 "하나의 이유로 바뀐 묶음"으로 나눈다.

- 기능 추가, 버그 수정, 리팩터링, 설정 변경은 서로 다른 커밋으로 분리한다.
- 테스트는 대상 코드와 같은 커밋에 둔다.
- 한 파일 안에 성격이 다른 변경이 섞여 있으면 `git add -p`로 나누는 방안을 제안한다.
- 변경이 하나의 단위라면 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<필요할 때만: 무엇을 왜 바꿨는지>

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

| type | 용도 |
| --- | --- |
| feat | 사용자에게 보이는 새 기능, UI 변경 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 그 외 |

규칙:

- 요약은 50자 안팎, 마침표 없이, 명령형 대신 "~추가", "~수정"처럼 간결한 명사형으로 쓴다.
- "무엇을 했는지"보다 "왜 필요한지"가 드러나게 쓴다. 자명하면 본문은 생략한다.
- 저장소의 기존 커밋 스타일이 있으면 그것을 따른다.
- 커밋 메시지 끝에 위 `Co-Authored-By` 줄을 붙인다. 사용자의 CLAUDE.md나 지시가 다르면 그쪽을 따른다.

### 4. 커밋

승인을 기다리지 않고 커밋 단위마다 파일을 명시해서 스테이징하고 커밋한다.

```bash
git add <파일...>        # git add -A, git add . 는 쓰지 않는다
git commit -m "$(cat <<'EOF'
feat: 요약

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
EOF
)"
```

- 커밋 후 `git log --oneline -n <커밋 수>`로 결과와 제외한 파일(이유 포함)을 보고한다.
- 사용자가 수정을 요청하면 `git commit --amend`나 새 커밋으로 반영한다.
- hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 고친 뒤 새 커밋으로 만든다.
- 푸시는 사용자가 따로 요청할 때만 한다.
